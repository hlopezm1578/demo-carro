## Production Parity & Routing Contract (DEPL-02 — lo único nuevo de esta fase)

### Inventario de rutas (verificado por grep sobre `docs/05_desarrollo/` esta sesión)

| Ruta | Pantalla | Contratada en |
|------|----------|---------------|
| `/` | Landing | 01-UI-SPEC |
| `/productos` · `/productos/:id` | Catálogo · Ficha | 01-UI-SPEC |
| `/login` · `/registro` | Cuentas | 02-UI-SPEC |
| `/carro` · `/checkout` | Carro · Checkout protegido | 02-UI-SPEC |
| `/pago/resultado` | Resultado del pago | guías fase 3 (consumió tokens 01/02) |
| `/pedidos` · `/pedidos/:numero` | Historial · Voucher | guías fase 3 (ídem) |
| `/admin` · `/admin/pedidos` · `/admin/metricas` | Panel admin | 04-UI-SPEC |
| `*` | 404 NoEncontrado | 01-UI-SPEC |

**Regla DEPL-02:** el refresh o deep-link de CUALQUIER ruta de la tabla debe responder 200
sirviendo la SPA (`index.html`), jamás el 404 de plataforma. La mini-verificación de la guía
de deploy del frontend ejercita como mínimo las rutas profundas: `/pago/resultado`,
`/pedidos/:numero`, `/admin/pedidos`, `/productos/:id`.

### El rewrite es EL entregable (configuración, no código)

Vercel no infiere que el proyecto es SPA: el fallback exige un `vercel.json` commiteado en la
raíz del proyecto Vercel, junto al `package.json` del frontend (Pattern 2 de `05-RESEARCH.md`,
citando la KB oficial de Vercel):

```json
{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

Síntoma exacto de DEPL-02 sin configurar: la tienda funciona navegando desde `/` pero da 404
al refresh o deep-link de una ruta profunda.

### La cadena crítica que el rewrite sostiene (el retorno de Webpay ES un full-page load)

1. Webpay devuelve el navegador (GET o POST, ADR-012) al `return_url` público congelado:
   `{BACKEND_URL}/api/pago/retorno` (env var de Render).
2. El backend discrimina por presencia de params, commitea si hay `token_ws` y responde
   **302 explícito** a `{cors_origins[0]}/pago/resultado?…` (guia-09, byte-exacto).
3. El navegador hace un full-page GET a esa ruta profunda de la SPA pública → sin rewrite,
   este paso es un 404 de plataforma y TODO el flujo de pago muere en producción. **El
   rewrite ES el DEPL-02.**
4. La SPA hidrata y pinta el resultado/voucher con el título decidido por el estado REAL del
   pedido fetcheado (no por el query param del 302) — comportamiento de fase 3, sin cambios.

**Carro y sesión sobreviven el retorno (CART-02/D-27 heredados):** el 302 vuelve al MISMO
origen público de la SPA (`cors_origins[0]`), por lo que localStorage (carro + token) cruza
el full-page load exactamente igual que en dev. Congelar `CORS_ORIGINS` a la URL de Vercel no
es solo CORS: es el destino del 302.

### Cold start (comportamiento aceptado, no UI nueva)

Render free duerme a los ~15 min sin tráfico y despierta en ~1 min (cifras de las docs
oficiales de Render citadas con URL en `05-RESEARCH.md`, "a la fecha" — D-73: evidencia
documental, no runtime). La SPA estática carga al instante (Vercel no duerme); las llamadas a la API
quedan en `isPending` → skeletons heredados `animate-pulse` hasta por ~1 minuto. **No se
contrata pantalla, banner ni badge "despertando"**: la guía/doc 07 lo nombran en prosa para
el alumno (specifics de CONTEXT — nombrarlo honestamente, no esconderlo). Si el fetch falla,
aplica el estado de error heredado y el botón "Reintentar" (`refetch()`) — que es
accidentalmente la UX correcta: cada reintento ayuda a despertar el servicio.

### Paridad cero drift (criterio de aceptación visual de la fase)

La verificación de fase 5 NO es "se ve bien" sino "es idéntico": las pantallas 1-14 y todos
sus estados en la URL pública deben corresponder 1:1 con lo contratado en 01/02/04 (+ las
pantallas 8-9 de las guías de fase 3). Cualquier diferencia visual en producción es un
defecto de build/entorno, no una decisión de diseño nueva. Síntomas conocidos (Pitfalls 3 del
research): la SPA pidiendo a `localhost` o `//api` en Network = `VITE_API_URL` mal horneada
(o cambiada sin redeploy); fuente por defecto del sistema = assets de Nunito fuera del build.

### Caveat heredado aceptado: familia de copies "puerto 8000" (con regla de decisión)

La familia de copies de error "Revisa que el backend esté corriendo en el puerto 8000 e
inténtalo de nuevo." está locked en las guías 02-15 (presente en 8 guías, verificado por grep
esta sesión) y llega tal cual a producción si la API no responde. Es wording de entorno de
desarrollo visto por una clienta: **aceptado para esta fase** (la serie jamás re-edita guías
construidas; cambiar el copy de la app sería código nuevo fuera del alcance del deploy, y
CONTEXT declaró "ninguno esperado"). **Regla de decisión (re-anclada a D-73):** si la
evidencia viva lo declara defecto real de experiencia en producción — feedback del alumno
desde sus mini-verificaciones/Gran verificación final, o el doc 08 de mantenimiento —,
se corrige por la regla de bugs en
AMBOS lugares (guía + taller maura-uat) Y se registra como amendment a este spec — nunca en
silencio.

### Camino de amendment (si aparece evidencia viva)

CONTEXT dejó la puerta: "DFDs/pantallas solo si aparece evidencia viva". Si la evidencia
documental (docs de plataforma citadas en `05-RESEARCH.md`) o el feedback del alumno en
producción revelan que el ambiente desplegado necesita una pantalla/estado/copys nuevos
(p. ej. una plataforma exige un interstitial), ESTE spec se enmienda ANTES de redactar la guía que lo
enseña — mismo mecanismo que el Amendment 2026-09-29 de fase 1. Prohibido improvisar copys
de UI directamente en guia-16+.
